    Logging, evaluation and checkpoints¶

    See Logging and Checkpoints and resuming.

    ajax.logging.backends ¶

    Where a run's logs go: backends behind one small protocol.

    Every evaluation a run logs reaches each of its backends in the logging worker, a process of its own, so that training never waits on a disk or a network. The worker is spawned (CUDA is never forked), so a backend is built in the caller's process and copied into the worker: it must be picklable, and it learns about runs only through the calls below. One backend object serves every run of a train call (one run per seed).

    RunInfo dataclass ¶

    RunInfo(run_id, name, config, seed=None)

    What a backend is told when a run opens.

    run_id: 8 base-36 characters, unique to the run (W&B's id format). name: the LoggingConfig's run_name and the id, "_". config: the LoggingConfig's config, with the agent's run configuration merged in. In the worker, its values that are not JSON (an environment object, a function) are their text. seed: the run's seed, when the caller gives it.

    LoggingBackend ¶

    Bases: Protocol

    A sink for the evaluations runs log: any picklable object with these three methods, all called in the logging worker.

    A backend may also have start(run), called in the caller's process for each run before training starts, for what must happen at once (W&B creates its run there, so a missing account fails before training and the run shows in the W&B UI at once). What a backend gathers in the worker stays there: to get it back, write it to a file.

    A backend of your own, here one printing each step:

    class PrintBackend:
    def open(self, run):
        print("run", run.name, "seed", run.seed)

    def log(self, run_id, step, metrics):
        print(run_id, step, {k: v.tolist() for k, v in metrics.items()})

    def close(self):
        pass

LoggingConfig(backends=(PrintBackend(), TensorBoardBackend("runs")))

    It reaches the worker by pickling, so its class must be importable there: defined in a module or a script, not in a notebook cell.

    open ¶

    open(run)

    A run starts; called before its first log.

    log ¶

    log(run_id, step, metrics)

    One evaluation of a run: its metrics at environment step step, each a numpy array. Metrics that are NaN (not computed at this step) are left out.

    close ¶

    close()

    Training ended: write out anything buffered and release files.

    TensorBoardBackend dataclass ¶

    TensorBoardBackend(folder='.')

    TensorBoard event files, a folder per run: folder/tensorboard//, beside the run's config.json (its configuration, seed and id, so runs can be found and paired by seed). Metrics that are not one number are left out.

    WandbBackend dataclass ¶

    WandbBackend(
    project=None, group=None, batch_size=10, steps=True
)

    Weights & Biases: the wandb extra (pip install ajax-rl[wandb]) and an account. wandb keeps one open run per process, so a run's steps are sent in batches of batch_size, each batch in one init, log, finish cycle; the run is created when training starts so it shows in the W&B UI at once. With steps=False the run is created and gets no evaluation, as a W&B sweep's runs did with use_wandb and sweep=True.

    ajax.logging.wandb_logging ¶

    LoggingConfig and the logging worker, which passes every run's evaluations to its backends (ajax.logging.backends).

    LoggingConfig ¶

    Evaluation and logging for a train call: every log_frequency environment steps the agent is evaluated, train returns the evaluations, and each run (one per seed) logs them to the backends.

    the LoggingBackend objects every run logs to, such as

    TensorBoardBackend(folder) and WandbBackend(project, group), or one of your own (see LoggingBackend); backends=() logs nowhere, and train still returns the evaluations. Not given, use_wandb (on unless set False) and use_tensorboard (off unless set True) name them, as before; given, setting either flag as well is refused.

    config: stored with each run, with the agent's run configuration merged in. project_name, group_name: the W&B project and group of use_wandb. run_name: the prefix of each run's name, "_". log_frequency: environment steps between evaluations. folder: where use_tensorboard writes, folder/tensorboard// (the working directory when None). sweep: for hyperparameter sweeps, evaluate only in the last fifth of training; with use_wandb, the W&B run gets no steps (WandbBackend(steps=False)).

    run_backends property ¶

    run_backends

    The backends every run logs to: backends, else those the flags name, else TensorBoard's (folder/tensorboard//).

    backend property ¶

    backend

    Whether a run writes anywhere, so needs the logging worker; without a backend it still evaluates (train returns the evaluations).

    with_agent_config ¶

    with_agent_config(agent_config)

    The copy a train call logs with: the agent's run configuration merged into config, and the backends named, so the flags are read (and warned about) once. A copy, so one LoggingConfig can serve several agents' runs.

    new_run_id ¶

    new_run_id()

    A fresh run id in W&B's format (wandb.sdk.lib.runid.generate_id: 8 random base-36 digits), without importing wandb.

    start_async_logging ¶

    start_async_logging()

    Spawn the logging process (once; no-op if already running).

    stop_async_logging ¶

    stop_async_logging()

    Drain the queue, then stop the logging process.

    init_logging ¶

    init_logging(run_id, logging_config, run_seed=None)

    Register a run with the logging config's backends: each backend's start, if it has one, runs here, before training (W&B creates the run, so it appears in the W&B UI immediately); the worker then opens the run.

    When run_seed is given (one call per seed), it is recorded alongside the config so every run is reproducible and can be paired across conditions by seed (see the per-run config.json written for TensorBoard runs).

    ajax.evaluate ¶

    ValueEstimate dataclass ¶

    ValueEstimate(value, gamma, reward_scale=1.0)

    An agent's critic, read for the value bias :func:evaluate returns: value(agent_state, obs, action) is its estimate (one per env) of the return from obs taking action, of the rewards times reward_scale discounted by gamma, as its targets are.

    normalised_reward ¶

    normalised_reward(x, norm_info)

    x, a reward or a sum of rewards in the env's units, in the agent's: divided by the scale the training env's reward normaliser holds (norm_info.reward, frozen), as collection divides each reward; unchanged without one.

    setup_environment ¶

    setup_environment(
    env,
    env_params,
    num_episodes,
    norm_info,
    gamma,
    action_repeat=1,
    episode_length=None,
)

    The training env's stack, rebuilt for evaluation (gymnax or brax).

    Ajax's own layers come off (:func:~ajax.environments.create.strip_ajax_wrappers) and go back on as training composed them (:func:~ajax.environments.create.add_ajax_wrappers): the clip to a continuous action space's bounds, the observation normaliser frozen at norm_info (None: no normaliser) and applied to the observations only where training applied it, rewards never normalised. The task under them -- the user's wrappers, the flattening -- is kept as trained on (gymnax).

    brax / playground tasks are rebuilt from their id with num_episodes parallel envs, and the wrappers over the stack the builder returned go back over the rebuilt one. episode_length (simulator steps) and action_repeat are the training env's; the defaults are None -> the env's native episode length, falling back to 1000, and repeat 1. gymnax envs do not support action_repeat > 1.

    get_deterministic_action_and_entropy_fn ¶

    get_deterministic_action_and_entropy_fn(
    actor_state, recurrent, continuous
)

    Return a function mapping (obs, done, hidden) → (action, entropy, hidden).

    In recurrent mode the hidden state is an explicit input/output so the eval loop can thread it through its carry (the live carry on actor_state belongs to the training envs and has the wrong batch size here). Non-recurrent mode passes hidden through untouched.

    step_environment ¶

    step_environment(
    mode,
    env,
    env_params,
    recurrent,
    actor_state,
    continuous,
    expert_policy=None,
    agent_state=None,
    controller=None,
    value_estimate=None,
    command=None,
    norm_info=None,
)

    Return a pure function stepping the evaluation (an :class:_EvalCarry).

    Each step acts as the agent's controller says, on an :class:~ajax.controller.ActingState built from the carry: the actor's input (:meth:~ajax.controller.Controller.observe), its deterministic action, then the executed one (:meth:~ajax.controller.Controller.act). The expert acts in agent units (:class:ExpertInAgentUnits), as every action here; the executed one is mapped onto the env's bounds (:func:agent_action_to_env), as in collection. The expert's state is tracked from the actor's input on, statefully, as collection tracks it, and restarts with each episode.

    value_estimate: the critic's estimate at the actor's input and the action collection stores, each step: the executed action in agent units, the actor's (the gains') under gain mode.

    command: a command-conditioned actor's (see :func:evaluate): the actor reads command.actor_input(obs, c), and each step's reward, in the agent's units (norm_info, :func:normalised_reward), and end update c.

    The controller's choosers (an extension's eval_action phase) may then replace the executed action by the expert's (choose_in_evaluation), on keys derived from the carry's: they move no other draw.

    step_environment_expert ¶

    step_environment_expert(
    mode, env, env_params, expert_policy
)

    Step function for the expert's own rollout, called as the agent's rollout calls it (:func:step_environment): a stateful expert (one with init_state) as expert_policy(state, obs) -> (action, state), a stateless one as expert_policy(obs) -> action, in agent units and mapped onto the env's bounds. A discrete expert's action index comes as an (n, 1) column, as a replay keeps it; the env takes (n,).

    evaluate ¶

    evaluate(
    env,
    actor_state,
    num_episodes,
    rng,
    env_params,
    recurrent=False,
    gamma=0.99,
    norm_info=None,
    avg_reward_mode=False,
    expert_policy=None,
    max_eval_steps=None,
    agent_state=None,
    controller=None,
    eval_expert_policy=None,
    value_estimate=None,
    command=None,
)

    Evaluate the actor's deterministic policy on num_episodes episodes; with expert_policy (the training expert, which builds the actor's input) the expert's return too, that of eval_expert_policy when given, on the same episodes (the same reset and key). The experts speak env units: they are read in agent units here (:class:ExpertInAgentUnits; an agent's are already).

    command evaluates a command-conditioned actor (UDRL's desired return and horizon): command.initial(agent_state, num_episodes) is each episode's first command, the actor reads command.actor_input(obs, c), and command.update(c, reward, done) follows each step, the reward in the agent's units, normalised as in training: the units of its targets.

    Returns the mean return, entropy, average reward (avg_reward_mode), value bias (value_estimate), episode length and expert's return, each NaN without what it needs. The value bias is the mean over the evaluated steps of the critic's estimate (:class:ValueEstimate) minus the discounted return realised from the step, in the critic's units: the rewards normalised as in training (:func:normalised_reward) and scaled. A recurrent critic's memory is not run here: NaN then. A controller with choosers (step_environment) adds a seventh: the share of the evaluated steps they handed the expert.

    evaluate_policy ¶

    evaluate_policy(
    env_args,
    policy_fn,
    init_carry_fn,
    num_episodes,
    key,
    agent_state=None,
)

    Mean return and mean length of one episode in each of num_episodes envs.

    The evaluation protocol of the agents that own their collection (the world-model agents, DESIGN §5.4), for a stateful policy with the row collector's protocol policy_fn(carry, obs, is_first, key) -> (action, carry, extras) (extras ignored):

    • the env is rebuilt through :func:setup_environment with num_episodes parallel envs and the training action_repeat and episode length; actions go through :func:ajax.environments.utils.agent_action_to_env, as in the row collector, so train and eval act on the env identically (the env's clip to its bounds is then a no-op);
    • the envs are reset with key (the same reset-key derivation as :func:evaluate, so both see the same initial states for one key);
    • the policy starts from init_carry_fn(num_episodes) (a zero carry) with is_first set on the first step only;
    • every env runs exactly one episode: a scan over the episode length in agent steps (:func:ajax.environments.utils.agent_episode_length) with rewards and lengths masked after each env's first done;
    • every observation carries its features (env_args.observers) at the progress the collector of agent_state holds, frozen as evaluate holds it.

    Preconditions (they raise): the training env does not normalise observations or rewards (the rebuild is the raw env, see :func:ajax.environments.row_collector.check_unnormalized_env), and env_params describes one system (per-env, batched params cannot be rebuilt with num_episodes envs; evaluate a nominal system instead).

    ajax.checkpoint ¶

    Checkpoint save/restore for Ajax agents.

    Serializes the pytree data of a BaseAgentState (arrays, counters, and other leaves) while discarding non-data fields such as optax GradientTransformation closures and flax apply_fn callables. Those closures are rebuilt at load time by re-initializing a skeleton state from the same agent config; the loaded data is then grafted onto the skeleton via flax.serialization.from_state_dict.

    Typical resume flow (resume in tests/probing/runs.py runs it): skeleton = agent.train(seed=seeds, n_timesteps=0) # init only if checkpoint_exists(path): skeleton = restore_into(skeleton, path) final = agent.train(..., initial_state=skeleton, ...) save_checkpoint(final, path)

    save_checkpoint ¶

    save_checkpoint(state, path)

    Save the pytree data of state to path. Atomic write.

    restore_into ¶

    restore_into(skeleton, path)

    Load path and graft its data onto skeleton.

    skeleton is a freshly-initialized agent state with the same structure as the saved one. The optimizer transformations and apply functions come from skeleton; only the pytree data (params, optimizer mu/nu/count, buffer arrays, rngs, counters) is replaced.
